В целевой архитектуре **ESB (Apache Camel) полностью выводится из эксплуатации** как централизованная шина. Его функции распределяются между **Integration Layer (Kafka + Stream Processing)**, **доменными микросервисами** и **слоем витрин данных**. 

Ниже приведена **таблица миграции функциональности ESB**.

---

### Распределение функциональности ESB по целевым слоям

| Функция ESB (Apache Camel) | Куда переезжает | Обоснование (соответствие бизнес-целям) |
| :--- | :--- | :--- |
| **Маршрутизация (Routing)** | **Integration Layer (Kafka)** — топики по доменам, Consumer Groups. | Децентрализация: домены сами подписываются на нужные события. Снижение единой точки отказа (SPOF). |
| **Трансформации (Mapping/Transformation)** | **1. Потоковые (Stream):** <br>**Kafka Streams / Flink** (в Integration Layer). <br>**2. Пакетные (Batch):** <br>**ETL-сервисы** (Python/Go) в домене **Аналитики** (или оркестрация Airflow). | Четкое разделение: потоковые — для витрин реального времени, пакетные — для тяжелых отчетов. Ускорение обработки за счет масштабирования в облаке. |
| **Валидация и ФЛК (Формально-логический контроль)** | **Domain Services** (на входе) + **Integration Layer** (схемы Avro/Protobuf в Schema Registry). | "Shift-Left" (смещение влево): валидация на границе домена (Fast Fail) и проверка схем на уровне шины (гарантия качества данных). |
| **Патерны надежности (Retry, DLQ, Circuit Breaker)** | **Integration Layer (Kafka)** — настройки потребителей (Retry, Dead Letter Queue) + **Kubernetes** (liveness/readiness probes) для микросервисов. | Отказоустойчивость обеспечивается на уровне инфраструктуры (K8s) и протокола (Kafka-commit), а не через монолитную ESB-логику. |
| **Бизнес-логика (Orchestration)** | **Domain Microservices** (Golang/Java/Python) — владеют своими процессами. <br>Взаимодействие через **асинхронные события (Kafka)**, синхронные — через **gRPC/REST API**. | Независимость доменов: изменения в логике одного бизнеса не требуют переделки маршрутов в ESB. Ускорение Time-to-Market. |
| **Агрегация данных (для отчетов)** | **Слой витрин данных (ClickHouse/Azure Synapse)** — materialized views, агрегационные таблицы. | Высокая производительность аналитики (доли секунды вместо часов), так как агрегация выполняется на специализированных колоночных СУБД. |
| **Мониторинг трафика** | **Service Mesh (Istio/Linkerd)** + **Grafana/Prometheus** + **Kafka Monitoring (Burrow)**. | Глубокая наблюдаемость (observability): сбор метрик на уровне сети, приложения и потоков данных. |

### Описание потоков данных с учетом миграции ESB

1.  **Источник (Клиника)** → **Domain API (gRPC)**.
    *   Валидация ФЛК на входе (проверка структуры данных).
    *   Сохранение в Операционную БД.
2.  **Domain API** → **Integration Layer (Kafka)**.
    *   Публикация события (например, `PatientRegistered`).
    *   **Перехват трансформаций:** Kafka Streams обогащает событие данными из справочников (вместо маршрутов Camel).
3.  **Integration Layer (Streams)** → **Слой витрин (ClickHouse)**.
    *   Запись в real-time витрины для оперативной отчетности.
4.  **Integration Layer (Kafka)** → **Domain Analytics (Airflow)** → **Слой витрин (Synapse)**.
    *   Пакетная выгрузка в озеро данных, где выполняются тяжелые трансформации для финансовой отчетности.
5.  **Портал самообслуживания** → **Слой витрин (ClickHouse)**.
    *   Прямые запросы (SQL) к подготовленным агрегатам, минуя любые трансформации на лету.

---

**Ключевой вывод:** 
Старая ESB-шина ликвидируется. **ФЛК и потоковые трансформации** переходят в **Kafka Streams**, **паттерны надежности** — в **Kubernetes и настройки Kafka Consumer**, **бизнес-логика** — в **микросервисы доменов**, а **пакетные трансформации** выделяются в отдельный слой **Airflow**. Это убирает монолитную связанность и позволяет масштабировать каждую функцию (потоки, батчи, бизнес-сервисы) отдельно.
