### 1. Целевая архитектура системы через год (диаграмма контейнеров в модели C4)

Ниже представлено текстовое описание диаграммы контейнеров C4, схема в файле Task1\containerC4.drawio
---

**Контейнеры (C4 level 2):**

1. **Портал самообслуживания (Data Portal)**  
   - Веб-приложение для бизнес-пользователей.  
   - Предоставляет доступ к витринам данных (без медицинских карт, историй болезней, результатов исследований).  
   - Поддерживает конструирование собственных отчётов и предварительно настроенные дашборды.  
   - Интегрируется с системами авторизации и управления доступом (RBAC/ABAC).  
   - Сценарии: быстрая подготовка отчётности, самостоятельный анализ данных, снижение нагрузки на ИТ-команду.

2. **Слой витрин данных (Data Marts Layer)**  
   - Набор хранилищ (OLAP, колоночные СУБД, например, ClickHouse или Azure Synapse).  
   - Витрины организованы по доменам:  
     - Финансовая витрина (счета, кредиты, финансовая история, отчётность).  
     - Операционная витрина (клиенты, персонал, инвентаризация).  
     - Агрегированная витрина для кросс-доменных отчётов (KPI, управленческая отчётность).  
   - Данные денормализованы и оптимизированы для чтения.  
   - Сценарии: масштабирование под новые бизнесы, независимое развитие доменов, снижение трансформаций в DWH.

3. **Слой интеграции (Integration Layer)**  
   - Современная шина данных (например, Apache Kafka + Debezium, или облачный Event Hub).  
   - Обеспечивает потоковую и пакетную передачу данных между доменами.  
   - Реализует публикацию событий изменений (CDC) из систем-источников.  
   - Сценарии: подключение новых бизнес-направлений без изменения DWH, отделение бизнес-логики от хранилища.

4. **Домен «Клиники» (Clinics Domain)**  
   - Легаси DWH на SQL Server 2008 (временное сохранение).  
   - Миграция бизнес-логики в микросервисы (на Go/Java) и слой витрин.  
   - Интерфейс операторов на PowerBuilder (планируется замена).  
   - Сценарии: продолжение работы клиник в переходный период.

5. **Домен «Финтех» (Fintech Domain)**  
   - Микросервисы на Go/Java для банковских и финансовых операций.  
   - Собственная операционная БД (PostgreSQL или аналоги).  
   - Публикует события в Integration Layer для витрин.  
   - Сценарии: независимое развитие финтех-услуг, соответствие регуляторным требованиям.

6. **Домен «ИИ-сервисы» (AI Domain)**  
   - Микросервисы на Python для обработки медицинских данных (диагностика, лечение).  
   - Работает с медицинскими картами, историями болезней, результатами исследований.  
   - Данные не передаются в витрины самообслуживания.  
   - Сценарии: качество медицинских сервисов, независимое развитие ИИ.

7. **Система управления доступом и безопасностью (IAM & Security)**  
   - Централизованный сервис аутентификации/авторизации.  
   - Политики доступа на уровне записей (для медицинских и финансовых данных).  
   - Сценарии: соблюдение требований регуляторов, защита чувствительных данных.

8. **BI-система (Power BI)**  
   - Сохранена, но переключена на витрины данных вместо прямого доступа к DWH.  
   - Кастомизации вынесены в слой витрин или в портал самообслуживания.  
   - Сценарии: управленческая отчётность, снижение времени формирования отчётов.

---

**Взаимодействие (ключевые потоки):**

- Источники (Клиники, Финтех, ИИ) → Integration Layer (события/CDC) → Трансформации (легкие, без бизнес-логики) → Витрины данных → Портал самообслуживания и BI.  
- Запросы от портала → Витрины (без обращения к источникам).  
- Управление доступом → Проверка прав при каждом запросе к витринам.

---

**Поддержка бизнес-сценариев на диаграмме:**

| Бизнес-сценарий | Механизм в целевой архитектуре |
|----------------|--------------------------------|
| Быстрая подготовка отчётности | Витрины данных, оптимизированные для чтения; портал самообслуживания с кэшированием и предрасчётом. |
| Независимое развитие финтех и ИИ | Домены изолированы, интеграция через события; изменения в одном домене не влияют на другие. |
| Масштабирование для новых бизнесов | Подключение через Integration Layer (публикация событий) без изменения существующих витрин и логики. |
| Соблюдение регуляторных требований | Отсутствие медицинских данных в витринах; централизованная IAM; аудит доступа. |
| Снижение затрат на поддержку легаси | Поэтапная миграция, временное сохранение DWH только в домене «Клиники». |

### 2. Проблемные места текущей архитектуры

| № | Проблема | Описание | Пострадавшие бизнес-сценарии |
|---|----------|----------|------------------------------|
| 1 | Долгое формирование сложных отчётов (часы) | DWH на SQL Server 2008 не оптимизирован для аналитических запросов большого объёма (сотни ТБ). Множество трансформаций. | Управленческие решения задерживаются; снижение оперативности реагирования на изменения рынка. |
| 2 | Смешение бизнес-логики в DWH | Значительная часть логики реализована в хранимых процедурах и ETL, что усложняет изменение и масштабирование. | Замедление вывода новых фич (time-to-market); высокие риски при изменениях. |
| 3 | Высокая связанность доменов | Клиники, финтех, ИИ используют общий DWH, изменения влияют на все направления. | Невозможность независимого развития; конфликты при обновлениях. |
| 4 | Устаревшие технологии (SQL Server 2008, PowerBuilder, ESB на Apache Camel) | Ограниченная производительность, отсутствие современной поддержки, сложность интеграции с облаком. | Затраты на поддержку; риск несовместимости с новыми сервисами; сложность найма специалистов. |
| 5 | Отсутствие чётких границ данных для аналитики | Медицинские данные потенциально могут попасть в отчёты (риск нарушения регуляторных требований). | Юридические риски, штрафы, потеря доверия. |
| 6 | Нет портала самообслуживания | Все отчёты разрабатываются через BI-команду, кастомизации поверх DWH. | Долгий цикл получения отчётов; нагрузка на ИТ; негибкость. |
| 7 | Единая шина данных (ESB) как узкое место | Apache Camel в старой версии не справляется с потоковой нагрузкой и масштабированием. | Задержки в интеграции новых источников; отказы при пиковых нагрузках. |
| 8 | Отсутствие геораспределённости и отказоустойчивости | Системы развёрнуты локально, нет резервирования. | Риск недоступности критичных сервисов (клиники, финтех). |

### 3. Приоритизация проблем (матрица Эйзенхауэра)

*Критерии приоритизации:*  
- **Срочность** — влияние на текущие операции и выручку.  
- **Важность** — влияние на стратегические цели (выход на рынок, качество сервисов, регуляторка).

| Проблема | Срочность | Важность | Приоритет | Обоснование |
|----------|-----------|----------|-----------|-------------|
| 1. Долгое формирование отчётов | Высокая | Высокая | **Сделать сейчас** | Напрямую влияет на скорость принятия решений, снижает эффективность управления. Критично для всех доменов. |
| 2. Смешение бизнес-логики в DWH | Средняя | Высокая | **Сделать сейчас** | Замедляет time-to-market для новых фичей, что критично для конкурентоспособности финтех и ИИ. |
| 3. Высокая связанность доменов | Средняя | Высокая | **Сделать сейчас** | Препятствует независимому развитию, что является одной из ключевых целей бизнеса. |
| 5. Отсутствие границ для медицинских данных | Высокая | Высокая | **Сделать сейчас** | Регуляторный риск — штрафы и потеря лицензий, критично для выручки и репутации. |
| 7. ESB как узкое место | Средняя | Средняя | **Запланировать** | Влияет на интеграцию новых направлений, но не блокирует текущие операции при имеющихся нагрузках. |
| 4. Устаревшие технологии (DWH, PowerBuilder) | Низкая | Средняя | **Запланировать** | Поддержка дорогая, но системы работают; миграция возможна поэтапно. |
| 6. Нет портала самообслуживания | Средняя | Средняя | **Запланировать** | Улучшает гибкость, но не критична для выручки в краткосрочной перспективе (есть BI). |
| 8. Отсутствие отказоустойчивости | Низкая | Средняя | **Решить позже** | Важно для надёжности, но пока нет инцидентов; облачная миграция частично решит это. |

---

**Связь с целями бизнеса:**

- Выручка → проблемы 1, 5 (задержки решений, регуляторные риски).  
- Скорость выхода на рынок → проблемы 2, 3 (зависимость доменов, логика в DWH).  
- Качество медицинских и финансовых сервисов → проблемы 3, 5, 7 (независимость доменов, защита данных, надёжность интеграции).
