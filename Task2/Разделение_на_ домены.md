### 1. Границы доменов и их обоснование

Разделение выполнено по принципу **предметной области (DDD - Domain-Driven Design)** с учётом бизнес-целей, регуляторных требований и сценариев использования. Каждый домен владеет своими операционными данными и бизнес-логикой, публикует события изменений через интеграционную шину.

| Домен | Ответственность | Ключевые сущности | Обоснование (бизнес-сценарии) |
|-------|----------------|-------------------|-------------------------------|
| **Клиники** | Управление пациентами, медицинскими записями, инвентаризацией, персоналом, лечебным процессом. | Пациенты, медицинские карты, истории болезней, результаты исследований, инвентарь, персонал, расписания. | Основной операционный домен. Обеспечивает непрерывность клинической деятельности. Медицинские данные не передаются в аналитические витрины по требованию бизнеса. Изменения в этом домене не должны влиять на финтех или ИИ. |
| **Финтех** | Банковские услуги: счета, кредиты, платежи, финансовая история, отчётность по регуляторам. | Счета, транзакции, кредитные договоры, платёжные поручения, клиенты (фин. профиль). | Требует отдельной банковской лицензии и строгого контроля. Сценарии: независимый выпуск новых финпродуктов, быстрая интеграция с партнёрами (платёжные системы). Не должен зависеть от клинических систем. |
| **ИИ-сервисы** | Обработка медицинских данных для диагностики, прогнозирования, рекомендаций лечения. | Модели ML, исследовательские датасеты (обезличенные), результаты работы моделей. | Сценарий: улучшение качества диагностики. Работает с чувствительными данными, но не предоставляет их для общей аналитики. Требует отдельной среды для экспериментов и быстрого обновления моделей без влияния на другие домены. |
| **Партнёры (фармацевтика, электроника)** - будущее | Интеграция с внешними организациями для поставок, логистики, совместных исследований. | Заказы на поставку, каталоги оборудования, данные о клинических испытаниях (обобщённые). | Сценарии: подключение новых бизнес-направлений без доработки DWH. Каждый партнёр имеет свои форматы данных, которые адаптируются на интеграционном слое. Не требует оперативных данных клиник. |
| **Аналитика и отчётность** (кросс-доменный) | Предоставление витрин данных для самообслуживания (без медицинских карт) и управленческой отчётности. | Агрегированные KPI, финансовая отчётность, операционные метрики (кол-во пациентов, загрузка персонала, оборот). | Обеспечивает единое представление по ключевым показателям. Домены публикуют только разрешённые данные. Сценарии: быстрая подготовка отчётов, конструирование пользовательских дашбордов. |

### 3. Обоснование логики разделения на домены (преимущества для бизнеса)

#### 3.1. Независимое развитие

- **Финтех** может обновлять кредитные системы, внедрять новые банковские продукты без согласования с клиниками.  
- **ИИ-сервисы** могут экспериментировать с моделями на изолированных данных, не влияя на операционные системы.  
- **Клиники** продолжают работать в своём ритме, даже если в финтехе происходят масштабные изменения.  
- **Партнёры** подключаются через стандартизированный интеграционный слой — не требуется модифицировать DWH.

#### 3.2. Ускорение вывода продуктов (time-to-market)

- Новый финансовый продукт (например, кредит на лечение) разрабатывается внутри домена «Финтех», использует свои API и не требует перестройки DWH.  
- ИИ-модель для диагностики может быть развёрнута в своём домене за 1-2 недели, без ожидания релизных циклов клинической системы.  
- Партнёр (фармкомпания) интегрируется через неделю, а не месяцы, т.к. нужен только согласованный формат событий.

#### 3.3. Снижение зависимости от DWH

- Бизнес-логика вынесена из DWH в доменные сервисы. DWH становится только хранилищем для исторических данных (и временно — легаси).  
- Новая аналитика строится на основе событий из интеграционного слоя, а не на прямом доступе к операционным БД. Это снижает нагрузку на клинические системы.  
- При отказе одного домена (например, ИИ) остальные продолжают работать — это повышает общую надёжность.

#### 3.4. Соответствие регуляторным требованиям

- Медицинские данные (карты, диагнозы) остаются внутри домена «Клиники» и не покидают его без специального разрешения.  
- Финансовые данные обрабатываются в домене с банковской лицензией, где реализованы необходимые механизмы аудита и шифрования.  
- Отчётность для регуляторов строится на основе данных соответствующего домена, без смешивания с медицинской информацией.

#### 3.5. Масштабируемость

- Каждый домен может масштабироваться по нагрузке независимо (например, больше реплик для ИИ-сервисов).  
- Добавление нового партнёра не требует изменений в других доменах — достаточно настроить адаптер в интеграционном слое.
