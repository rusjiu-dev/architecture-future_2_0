**Задание 3. Технологический радар и роадмап изменений**

---

## 1. Технологический радар (Technology Radar)

Радар структурирован по четырём квадрантам: **Инструменты**, **Платформы**, **Методологии**, **Языки и фреймворки**. Для каждой технологии указан статус (Текущая / Рекомендуемая / Экспериментальная / Устаревающая) и поддерживаемые бизнес-сценарии.

---

### Квадрант 1. Инструменты обработки данных

| Технология | Статус | Бизнес-сценарии |
|------------|--------|-----------------|
| **Microsoft SQL Server 2008** | Устаревающая | Легаси-хранилище, временная поддержка клинических операций. Заменяется. |
| **ClickHouse** | Рекомендуемая | Быстрая аналитика (витрины данных), отчёты в реальном времени, масштабирование до сотен ТБ. |
| **Azure Synapse Analytics** | Рекомендуемая | Облачное хранилище для витрин, интеграция с Power BI, эластичное масштабирование. |
| **Apache Kafka** | Рекомендуемая | Потоковая интеграция между доменами, подключение новых бизнесов, снижение связанности. |
| **Debezium** | Рекомендуемая | CDC из операционных БД, обеспечение актуальности витрин без ETL-скриптов. |
| **Redis** | Рекомендуемая | Кэширование отчётов и предварительных агрегатов, ускорение работы портала. |
| **Apache Airflow** | Рекомендуемая | Оркестрация батч-процессов, управление пайплайнами обновления витрин. |
| **Power BI** | Текущая (сохраняется) | Визуализация и управленческая отчётность, но переключается на витрины вместо прямого DWH. |

---

### Квадрант 2. Платформы и инфраструктура

| Технология | Статус | Бизнес-сценарии |
|------------|--------|-----------------|
| **Облачная инфраструктура (AWS/Azure/GCP)** | Рекомендуемая | Масштабируемость ресурсов, геораспределённость, отказоустойчивость, снижение CAPEX. |
| **Kubernetes (k8s)** | Рекомендуемая | Оркестрация микросервисов доменов, независимое масштабирование каждого направления. |
| **Terraform** | Рекомендуемая | Инфраструктура как код (IaC), быстрое развёртывание новых сред для доменов и партнёров. |
| **Istio / Service Mesh** | Экспериментальная | Управление трафиком между сервисами, observability, безопасность (mTLS) для критичных данных. |
| **Внутренний дата-центр (on-prem)** | Устаревающая | Постепенный вывод из эксплуатации, остаётся только для легаси-компонентов. |

---

### Квадрант 3. Методологии и архитектурные подходы

| Методология | Статус | Бизнес-сценарии |
|-------------|--------|-----------------|
| **Data Mesh** | Рекомендуемая | Децентрализованное владение данными по доменам, независимое развитие, подключение партнёров. |
| **Domain-Driven Design (DDD)** | Рекомендуемая | Чёткие границы доменов, изоляция бизнес-логики, ускорение изменений. |
| **Event-Driven Architecture (EDA)** | Рекомендуемая | Асинхронная интеграция через Kafka, слабая связанность, масштабируемость. |
| **Data Lakehouse (Delta Lake / Iceberg)** | Экспериментальная | Единое хранилище для сырых и структурированных данных, будущая замена DWH. |
| **DevOps / GitOps** | Рекомендуемая | Ускорение поставки изменений, автоматизация развёртывания, снижение рисков. |
| **ABAC (Attribute-Based Access Control)** | Рекомендуемая | Тонкая настройка доступа к данным, соответствие регуляторным требованиям. |
| **Agile / SAFe** | Текущая | Управление проектами, но требует усиления в части data-инженерных практик. |

---

### Квадрант 4. Языки, фреймворки и библиотеки

| Технология | Статус | Бизнес-сценарии |
|------------|--------|-----------------|
| **Python (FastAPI, Pandas, scikit-learn)** | Рекомендуемая | ИИ-сервисы, прототипирование, ML-пайплайны. |
| **Golang** | Рекомендуемая | Высокопроизводительные микросервисы (финтех, интеграционные адаптеры). |
| **Java (Spring Boot)** | Рекомендуемая | Миграция финтех-сервисов на современный стек, сохранение существующего кода. |
| **PowerBuilder** | Устаревающая | Интерфейс клиник — планируется замена на React/Vue.js. |
| **React / TypeScript** | Рекомендуемая | Новый интерфейс для портала самообслуживания и клиник. |
| **SQL (T-SQL, PostgreSQL PL/pgSQL)** | Текущая | Операционные БД и витрины; но бизнес-логика выносится из DWH. |
| **Apache Avro / Protobuf** | Рекомендуемая | Сериализация для потоковой передачи, поддержка Schema Registry. |

## 2. Роадмап изменений (Roadmap)

Роадмап разбит на **4 этапа** (кварталы) с привязкой к бизнес-целям. Каждый этап содержит проекты, ожидаемые результаты, ответственных и ресурсы.

---

### Этап 0. Подготовительный (Q0 — текущий квартал) — «Базис и согласование»

**Бизнес-цель:** Сформировать архитектурное решение, определить границы доменов и запустить пилотные проекты.

| Проект | Действия | Ожидаемый результат | Ответственные | Ресурсы |
|--------|----------|---------------------|---------------|---------|
| **Согласование архитектуры** | Утверждение целевой архитектуры, доменных границ, технологического радара. | Архитектурный документ, согласованный с бизнесом и ИТ. | Архитектурный комитет, CIO, руководители доменов | Время команды |
| **Выбор облачного провайдера** | Оценка Azure vs AWS, пилотное развёртывание инфраструктуры. | Выбран провайдер, подписаны контракты. | Инфраструктурная команда, закупки | Бюджет на облачные ресурсы |
| **Обучение команд** | Тренинги по Data Mesh, Kafka, DDD, облачным технологиям. | Команды владеют новыми методологиями. | HR, внешние тренеры | Бюджет на обучение |
| **Запуск пилота CDC** | Настроить Debezium на одной из систем (например, финтех БД) и поток в Kafka. | Рабочий прототип потоковой интеграции. | Инженеры данных, разработчики финтеха | 2 инженера, 2 недели |

**Обоснование:** Без согласованной архитектуры и обучения дальнейшие шаги будут хаотичны. Пилот CDC снижает риски на этапе миграции.

---

### Этап 1. Q1 — «Инфраструктура и интеграция»

**Бизнес-цель:** Обеспечить техническую базу для независимого развития доменов и начать миграцию данных в облако.

| Проект | Действия | Ожидаемый результат | Ответственные | Ресурсы |
|--------|----------|---------------------|---------------|---------|
| **Развёртывание облачной инфраструктуры** | Создать Kubernetes-кластер, настроить сети, IAM, мониторинг (Prometheus/Grafana). | Рабочая облачная среда для всех доменов. | Инфраструктурная команда | Cloud budget, 3 инженера |
| **Настройка интеграционного слоя (Kafka)** | Развернуть Kafka, Debezium, Schema Registry, настроить топики по доменам. | Потоковая шина готова к приёму данных из пилотных доменов. | Инженеры данных, DevOps | 2 инженера, 1 месяц |
| **Миграция DWH (исторические данные)** | Перенести нечувствительные данные (клиенты, финансы, инвентарь) в облачное хранилище (Azure Synapse). | Снижение нагрузки на SQL Server 2008, подготовка к созданию витрин. | Data-инженеры, администраторы БД | 3 инженера, 2 месяца |
| **Разработка ABAC-сервиса** | Создать централизованный сервис управления доступом на основе атрибутов (роли, домен, тип данных). | Тонкий контроль доступа к витринам и API. | Backend-разработчики (Go/Java) | 2 разработчика, 1 месяц |
| **Замена ESB (Apache Camel)** | Разработать адаптеры для перевода существующих интеграций на Kafka. | Снижение зависимости от устаревшей шины. | Интеграционная команда | 2 инженера, 1 месяц |

**Обоснование:** Облачная инфраструктура даёт масштабируемость, Kafka — слабую связанность, а ABAC — безопасность. Миграция исторических данных снижает нагрузку на легаси-систему.

---

### Этап 2. Q2 — «Создание витрин и портала самообслуживания»

**Бизнес-цель:** Запустить портал самообслуживания для бизнес-пользователей и обеспечить быструю отчётность.

| Проект | Действия | Ожидаемый результат | Ответственные | Ресурсы |
|--------|----------|---------------------|---------------|---------|
| **Проектирование и наполнение витрин** | Построить витрины (фин., опер., агрегированную) на ClickHouse или Synapse, с денормализованными схемами. | Витрины готовы к приёму запросов, содержат только разрешённые данные. | Data-инженеры, аналитики данных | 3 инженера, 2 месяца |
| **Разработка портала самообслуживания** | Веб-приложение (React) с конструктором отчётов, преднастроенными дашбордами, кэшированием (Redis). | MVP портала доступен для аналитиков и менеджеров. | Frontend-разработчики, backend (API Gateway) | 4 разработчика, 2 месяца |
| **Настройка потоков из доменов в витрины** | Настроить Stream Processing (Kafka Streams) для трансформации событий в витрины. | Витрины обновляются в реальном времени (stream) и батчами. | Инженеры данных, разработчики Kafka | 2 инженера, 1 месяц |
| **Интеграция Power BI с витринами** | Переключить дашборды с DWH на витрины, вынести кастомизации. | BI-отчёты работают быстрее, нагрузка на DWH снижена. | BI-разработчики | 1 инженер, 2 недели |
| **Тестирование производительности** | Нагрузочное тестирование портала и витрин (до 1000 одновременных запросов). | Система выдерживает пиковые нагрузки. | QA-команда, инфраструктура | 2 инженера, 2 недели |

**Обоснование:** Портал самообслуживания сокращает время получения отчётов с часов до секунд, разгружает ИТ-команду и даёт бизнесу гибкость. Витрины обеспечивают масштабируемость аналитики.

---

### Этап 3. Q3 — «Независимость доменов и миграция легаси»

**Бизнес-цель:** Обеспечить полную независимость клиник, финтеха и ИИ, завершить переход на новые сервисы.

| Проект | Действия | Ожидаемый результат | Ответственные | Ресурсы |
|--------|----------|---------------------|---------------|---------|
| **Вынос бизнес-логики из DWH** | Рефакторинг хранимых процедур и ETL-скриптов в микросервисы доменов (Go/Java). | DWH становится только хранилищем, вся логика — в доменах. | Разработчики доменов, data-инженеры | 4 разработчика, 2 месяца |
| **Миграция интерфейса клиник** | Замена PowerBuilder на React/Vue с интеграцией к новым сервисам. | Современный интерфейс, снижение затрат на поддержку. | Frontend-команда, backend-команда клиник | 3 разработчика, 2 месяца |
| **Запуск ИИ-сервисов в отдельном домене** | Развернуть ML-пайплайны, настроить API для клиник, анонимизатор для метрик. | ИИ-рекомендации работают в production, метрики идут в аналитику. | Data Science, ML-инженеры | 3 специалиста, 1.5 месяца |
| **Подключение пилотного партнёра** | Интеграция с фарм-компанией через адаптеры в интеграционном слое. | Партнёр получает обезличенные агрегаты, отправляет заказы. | Разработчики адаптеров, интеграция | 2 инженера, 1 месяц |
| **Отказоустойчивость и геораспределение** | Настроить репликацию Kafka, витрин и критичных сервисов в двух регионах. | Доступность 99.9% для критичных систем. | Инфраструктура, DevOps | 2 инженера, 1 месяц |

**Обоснование:** Вынос логики из DWH ускоряет изменения, сокращает time-to-market. Замена PowerBuilder снижает риски и затраты на поддержку. Подключение партнёров подтверждает масштабируемость архитектуры. Геораспределение повышает надёжность.

---

### Этап 4. Q4 — «Стабилизация, масштабирование и оптимизация»

**Бизнес-цель:** Полная реализация портала, тиражирование подхода на все направления и подготовка к новым бизнесам.

| Проект | Действия | Ожидаемый результат | Ответственные | Ресурсы |
|--------|----------|---------------------|---------------|---------|
| **Доработка портала (релиз 2.0)** | Расширение конструктора отчётов, добавление push-уведомлений, экспорт в Excel/PDF. | Полнофункциональный портал для всех категорий пользователей. | Frontend + backend | 2 разработчика, 1 месяц |
| **Масштабирование на все клиники** | Раскатка новых интерфейсов и сервисов во все филиалы. | Все клиники работают в новой среде. | Команда внедрения, DevOps | 2 инженера, 1.5 месяца |
| **Создание центров компетенций** | Выделить команды по платформе данных, интеграции, ИИ. | Устойчивая модель поддержки и развития. | HR, руководители доменов | Время, бюджеты |
| **Оптимизация затрат в облаке** | Автомасштабирование, резервирование инстансов, мониторинг расходов. | Снижение облачных затрат на 20–30%. | FinOps, инфраструктура | 1 инженер, постоянный процесс |
| **Разработка Data Lakehouse (пилот)** | Запустить пилот на Delta Lake для сырых данных (как резерв для будущих потребностей). | Прототип для возможной замены DWH в долгосрок. | Data-инженеры | 2 инженера, 2 месяца |
| **Аудит безопасности и регуляторная проверка** | Провести внешний аудит соответствия (ФСТЭК, ЦБ, медицинские регуляторы). | Сертификация архитектуры, устранение замечаний. | Безопасность, комплаенс | Внешний аудитор, внутренние юристы |

**Обоснование:** Стабилизация и масштабирование обеспечивают возврат инвестиций. Оптимизация затрат снижает TCO. Аудит гарантирует соблюдение требований, что критично для банковской и медицинской лицензий. Пилот Data Lakehouse создаёт задел для будущих инноваций.

## 3. Общее обоснование этапов (связь с бизнес-целями)

| Этап | Бизнес-эффект | Метрика успеха |
|------|---------------|----------------|

| **Q1** | Снижение затрат на поддержку, повышение надёжности. | Сокращение времени простоя, готовность облачной среды. |

| **Q4** | Масштабируемость, снижение TCO, регуляторное соответствие. | Затраты на облако снижены, аудит пройден без нарушений. |
