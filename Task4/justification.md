# Обоснование конфигурации Terraform

## 1. Выбор ресурсов и параметров

Note - для теста в облаке использовал оптимизированные настройки по cpu, meme, disc

### Виртуальные машины
- **Bastion VM (2 vCPU, 4 GB RAM, 20 GB SSD)**:
  - Минимальные ресурсы достаточны для SSH-шлюза и тоннелирования трафика.
  - Public IP позволяет администраторам подключаться извне.
  - 20 GB SSD — для ОС и логов.

- **Application VM (4 vCPU, 16 GB RAM, 30 GB boot + 100 GB data SSD)**:
  - 4 vCPU и 16 GB RAM — для запуска Kafka, ClickHouse, PostgreSQL и микросервисов в контейнерах.
  - 30 GB boot — для ОС и Docker-образов.
  - 100 GB data disk — для хранения данных БД, логов и файлов приложений. Отдельный диск упрощает бэкап и миграцию.

### Диски
- Использованы **network-ssd** для производительности (IOPS выше, чем HDD), критично для БД и потоковой обработки.
- Автоматическое создание снапшотов (daily, 7 дней) для data disk — защита от потери данных.

### Сеть
- **VPC с двумя подсетями**:
  - Public subnet — только для bastion, минимальная поверхность атаки.
  - Private subnet — для app-сервисов, доступ только через bastion.
- **NAT Gateway** — позволяет приложениям в private subnet обновлять пакеты и отправлять метрики вовне.
- **Security Groups** — реализуют принцип минимальных привилегий:
  - SSH разрешён только из публичной сети для bastion.
  - App VM принимает SSH только из public subnet (через bastion).
  - Внутренние порты (Kafka, ClickHouse) доступны только внутри VPC.

### Terraform Backend (S3)
- Использован remote state (S3-совместимый бакет) для совместной работы команды и предотвращения конфликтов.
- State хранится зашифрованным, доступ по ключам из переменных окружения.

## 2. Причины использования декларативного подхода (IaC)

- **Воспроизводимость**: Инфраструктура описывается кодом, что позволяет развернуть идентичную среду (dev/stage/prod) с минимальными изменениями.
- **Версионирование**: Все изменения проходят через Git → код-ревью → применение, что снижает риск человеческих ошибок.
- **Автоматизация**: `terraform apply` выполняется в CI/CD (например, GitLab CI), что ускоряет развёртывание после утверждения архитектуры.
- **Аудит и документация**: Код служит актуальной документацией инфраструктуры.

## 3. Как IaC способствует масштабируемости

- **Модульность**: Ресурсы сгруппированы в модули (VPC, VM, SG), что позволяет легко добавлять новые ВМ или кластеры.
- **Параметризация**: Через `variables.tf` можно менять размеры ВМ, количество реплик, CIDR сетей без переписывания кода.
- **Управление состоянием**: Remote state позволяет применять изменения параллельно нескольким инженерам.
- **Интеграция с другими инструментами**: После Terraform можно использовать Ansible/Helm для конфигурации ПО, что отделяет инфраструктуру от приложений.

## 4. Безопасность

- Чувствительные данные (токены, ключи) не хранятся в коде — передаются через переменные окружения или Vault.
- Bastion-хост ограничивает прямой доступ к внутренним сервисам.
- Security Groups реализуют network segmentation.
- Автоматические бэкапы дисков защищают от случайного удаления или сбоя.

## 5. Альтернативы и принятые решения

- **Managed Kubernetes** не использован в базовой конфигурации, т.к. на начальном этапе достаточно ВМ для развёртывания контейнеров через Docker Compose. В будущем k8s может быть добавлен как дополнительный модуль.
